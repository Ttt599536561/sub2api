# 福利签到 v2 已确认方案：惊喜频率、有限保底与成本

日期：2026-09-19。状态：**用户已确认采用 v2 签到算法，作为后续开发依据；尚未开发或上线，原型仍为固定演示数据。** 本文中的金额、概率和预算供项目所有者及开发内部参考；用户界面仍只写「今日惊喜，签到揭晓」与「神秘奖励」，签到成功后显示实际到账金额。

本次解决两个问题：消费何时累计；如何让每日奖励更有变化，同时控制成本。

## 1. 消费累计与页面刷新

建议分开处理两个时间：

- **实际账务结算：逐笔同步。** 在 API 真实余额扣款或批量图片 capture 的同一个数据库事务内写消费事实、增加福利累计消费。跨过 $50 门槛时，同时增加可用次数，无 10 秒或 1 分钟扫描任务。
- **前端显示：福利页面在前台时每 10 秒刷新轻量 overview。** 首次进入、恢复前台立即读取；签到／抽奖／兑换用响应中的新快照直接更新。隐藏或离开页面停止轮询，不重载日历和流水，不扫描或汇总 usage_logs。

现有项目部分结算由异步 worker 执行（例如 `backend/internal/handler/openai_gateway_handler.go:3262`）。因此「立即」指**结算事务提交后资格已经存在**，不是发送 API 请求时或每输出一个 token 时。未完成／尚未结算的请求稍后计入，不承诺请求返回后固定 10 秒内一定到账。

轮询请求不重叠；失焦停止、账号切换取消、过期 wallet_version 响应丢弃；错误／429 退避并遵循 Retry-After，轮询适当错峰。10,000 个同时停留前台的福利页在 10 秒间隔下约为 1,000 次 overview 请求／秒；此为前台在线量，不是注册用户数。上线前压测真实查询和鉴权链路，容量不足时调整显示策略或增加变更推送，账务仍保持逐笔同步。

### 性能边界（根据现有代码审查）

现有 `usage_billing_repo.Apply` 已经为每笔结算开启事务、写计费幂等键、扣账户余额，并按适用路径更新相关配额。福利累计应接入这一事务，不能另外遍历历史用量。按当前独立福利钱包方案，一笔合格结算主要多一个消费事实写入和一次用户福利累计更新，工作量随结算笔数线性增长；一笔结算不会随着该用户历史记录越来越多而重新扫描更多账单。

这不是零开销：还会增加 WAL、索引维护、存储和锁持有时间。同用户高并发要关注钱包行竞争，多个用户也仍共享数据库资源。消费明细只保存必要来源、金额和时间，不复制请求体、提示词或 token 全量详情；索引仅按去重、对账和退款查询需要设置，长期留存／归档需保留幂等和可追溯性。

异步结算 worker 只改变执行时点，并不减少数据库工作量。当前使用量记录池支持队列满时同步降级，不能宣称新增统计永远不会影响 API 响应；应观察计费任务积压、失败率及同步降级次数。不同路线也未必全部走异步结算。

实施先保留逐笔结算及短事务，事务中不进行 Redis／外部网络调用。压测至少比较基线与启用后的吞吐、p95/p99 结算耗时、锁等待、连接池占用、WAL／IO、队列积压，以及福利页 overview 的单独读取压力。不预设「支持多少 QPS」或「只增加百分之几」；依据部署硬件与实际峰值测量。

实现时还要避免把普通消费造成的钱包版本变化误当成兑换报价失效：兑换金额以专门的 `welfare_balance_version` 校验，仅福利余额改变时递增；用于整体状态同步的 `wallet_version` 仍反映消费进度等变更。否则高频 API 用户会因每笔消费都更新钱包版本而反复无法确认兑换。这属于首版实现必须同步到 DTO／报价任务的细节。

只有测量表明同步累计不能满足既有计费 SLO 时，才评估缩短 SQL 往返或调整计数位置；需要放宽即时性的持久事件微批处理属于后续明确的语义变更，不直接改成每 10 秒或每分钟全量扫描历史账单。

## 2. 原方案与三个选项

原型日历使用固定演示金额，并不是原概率表实际随机采样。原 v1 规则有 80% 日奖不高于 $0.10，单日期望 $0.07575；仅提高最高金额不能保证普通用户经常遇到较高奖励。

1. **独立随机加大中等奖励概率**：最简单，但会出现部分用户连续许多天只有小额，即使整体概率正确也不能解决这类体验。
2. **推荐：固定状态规则 + 最多 3 次连续小额**：兼顾每日变化和可计算成本；不同用户使用完全相同的状态转移规则。
3. **固定每第 3／4 天发大额**：成本易算，但节奏很快可预测。用户希望保留悬念，本轮不推荐。

用户已经选择第 2 项。v2 替代 v1「每天独立随机、没有保底」作为后续实现规则；v1 仅保留为成本对照，不与 v2 混用。设计获确认不代表功能已上线。

## 3. 第一步：决定普通奖励还是惊喜奖励

新增服务端字段 `daily_low_count`，记录自上次惊喜日奖之后，连续获得普通日奖的**成功签到次数**，取值 0–3。它与累计签到天数、30 天轮次天数是不同状态。

| 抽取前 daily_low_count | 当次惊喜奖励概率 | 普通奖励概率 |
|---:|---:|---:|
| 0 | 20% | 80% |
| 1 | 30% | 70% |
| 2 | 50% | 50% |
| 3 | 100% | 0% |

惊喜日奖到账后置 0；普通日奖到账后加 1。所以最多出现 3 次连续普通日奖，第 4 次成功签到必定是惊喜日奖；中间提前抽到惊喜就重新开始。

此处「惊喜」的内部定义是随机**日奖**至少 $0.10，不包含第 7／15／30 天额外连续奖励。例如当天日奖 $0.04、额外连续奖 $0.60，日奖计数仍按普通奖励处理。

建议 `daily_low_count` 在断签、自然月切换及 30 天签到轮次切换时保留，避免普通用户错过一天又重新经历连续小额。原有连续签到礼包进度仍按已确认规则断签清零。保底条件表达为「最多 4 次成功签到出现一次惊喜」；对每天连续签到用户，这意味着最多 4 天，不能给漏签用户承诺 4 个自然日内必得。

## 4. 第二步：抽取金额

### 普通日奖

范围 $0.01–$0.09：

- $0.01 的条件概率为 2%。
- $0.02–$0.09 合计条件概率为 98%，八个整数分值各 12.25%。

普通分支期望：`0.02×0.01 + 0.98×(0.02+0.09)/2 = $0.0541`。

### 惊喜日奖（建议上限 $1）

下表概率是**已经进入惊喜分支后的条件概率**，不是对所有签到直接应用的固定概率。

| 奖励范围 | 惊喜分支中的概率 | 区间均值 |
|---|---:|---:|
| $0.10–$0.20 | 65% | $0.15 |
| $0.21–$0.35 | 25% | $0.28 |
| $0.36–$0.50 | 9% | $0.43 |
| $0.51–$1.00 | 1% | $0.755 |

每个区间内按整数美分等概率抽取。惊喜分支期望为 `$0.21375`。

保留 $0.50 上限的对照方案：前三个区间权重改为 65%／25%／10%，取消最后一档，惊喜分支期望为 `$0.2105`。其余状态转移完全相同。

## 5. 实际体验与概率解释

从一次惊喜后的状态开始，到下次惊喜的间隔 T：

- `P(T=1)=0.20`
- `P(T=2)=0.80×0.30=0.24`
- `P(T=3)=0.80×0.70×0.50=0.28`
- `P(T=4)=0.80×0.70×0.50=0.28`

所以 `E(T)=2.64 次成功签到`，长期约 37.88% 的日奖属于惊喜，平均每 2.64 次签到出现一次。

- 长期约 **85.5%** 的每日奖励仍落在 $0.02–$0.20。
- 长期高于 $0.50 的每日奖励占约 **0.3788%**，约每 264 次签到出现一次；平均频率不等于保证。
- 对初始状态为 0、连续完成首个 30 次签到的用户：平均 **11.1384 次**获得至少 $0.10 的日奖。
- 首 30 次至少一次超过 $0.50 的概率约 **10.5812%**。
- 首 30 次至少一次恰好获得最高 $1 的概率约 **0.2225%**。提高上限不代表人人会拿到最高金额。

可能的 12 天日奖示意：`0.04 → 0.18 → 0.06 → 0.03 → 0.32 → 0.05 → 0.07 → 0.09 → 0.15 → 0.04 → 0.26 → 0.06`。这只是说明高低变化的一条合法序列，既不是模拟样本，也不是承诺；不含连续签到额外奖励。

v2 有历史状态和保底，不能对用户宣称每日都是同分布、相互独立的抽取。可用规则文案「多次签到未获得惊喜时，后续获得惊喜的机会会提高」解释机制，不提前公开金额。各用户应用相同配置，不依据用户身份、近期消费或运营预算临时压低个人概率。

## 6. 成本与是否放宽上限

以 `daily_low_count=0` 开始，使用 4 状态动态规划精确计算首 30 次签到。原定第 7／15／30 天额外奖励 $0.60／$2／$5，合计 $7.60，保持不变。

| 方案 | 首 30 次日奖期望 | 连续额外奖励 | 满勤首 30 天合计期望 |
|---|---:|---:|---:|
| 原 v1 独立随机，最高 $0.50 | $2.27250 | $7.60 | $9.87250 |
| v2 保底，最高 $0.50 | $3.36505 | $7.60 | $10.96505 |
| **v2 保底，最高 $1.00，推荐** | **$3.40125** | **$7.60** | **$11.00125** |

推荐方案相较原 v1 满勤总奖励约增加 **11.43%**。从 v2 的 $0.50 上限提高到 $1，上述 30 次期望仅增加 **$0.03620／人**，因为超过 $0.50 的分支很少。成本关键是出现频率与均值，而不是上限这个数字本身。

| 首轮全部满勤用户 | 原 v1 | 推荐 v2 | 期望增量 |
|---:|---:|---:|---:|
| 1,000 | $9,872.50 | $11,001.25 | $1,128.75 |
| 10,000 | $98,725.00 | $110,012.51 | $11,287.51 |

以上是发放站内余额的面值，不是实际供应商成本，且不包括消费抽奖返奖。消费抽奖奖表及每 $50 一次的规则本次不变。

长期稳态每日奖励期望为 `$0.11457348485`，稳态任意 30 次日奖期望约 `$3.43720`，加一轮完整连续奖励为 `$11.03720`。首轮由状态 0 开始略低，不能将首轮数据机械复用于每一轮；保底状态不随签到轮次重置。

长期比较，随机日奖部分的期望比 v1 增加约 **51.25%**；因为另有固定 $7.60 连续奖励，满勤总面值增加约 **11.80%**。预算讨论应同时说明这两个口径，不把日奖明显提高描述为成本不变。

期望不是硬预算上限。日奖最高改为 $1 后，30 天总理论最高是 `$30+$7.60=$37.60`；概率极低，但不能在财务上称为「每人每月最多 $11」。如设置运营预算预警，应告警或公开暂停新增活动，不在发奖时暗中修改中奖结果。

## 7. 可落地的整数算法

所有抽样使用服务端 `crypto/rand.Int` 均匀整数，读取与更新计数和记账放在同一签到事务里。

```text
BEGIN
  锁定福利钱包；同一业务日已签到则返回原结果
  n = daily_low_count  // 0..3
  surprise = randInt(100) < [20,30,50,100][n]
  if surprise:
    tier = 按整数权重[65,25,9,1]采样
    reward_cents = 在tier的闭区间内均匀采样
    next_low_count = 0
  else:
    // 总权重400：1分权重8；2..9分各49
    reward_cents = 从普通日奖整数表采样
    next_low_count = n + 1
  按既有连续签到规则另算里程碑奖励
  原子保存日奖、里程碑、next_low_count、签到日期与周期、钱包版本、余额和流水
  保存规则版本、抽样前后n、私有随机结果，供内部核验
COMMIT
```

同一业务日重试不增加 low_count、不再次抽取。随机源或事务失败均不发奖，不消耗保底进度；事务重试遵循原幂等与结果保存约定。固定演示原型仍可使用示例金额，但不能把它误当成真实算法采样结果。

## 8. 验证与落地边界

- 四状态转移概率各行合计 1，3 次普通之后普通分支概率为 0。
- 枚举普通 400 权重以及惊喜分支区间端点，验证金额完整覆盖和无越界。
- 每次成功签到只更新一次状态；并发、重复请求、跨午夜均沿用现有设计的幂等约束。
- 验证第 7／15／30 天额外奖励不影响 ordinary/surprise 判定和计数；断签只重置连续礼包进度。
- 成本用动态规划而非将 30 天当成独立样本。普通状态概率 d 更新为 `d'[0]=Σd[i]p[i]`、`d'[i+1]=d[i](1-p[i])`，累积每次惊喜概率得到期望惊喜次数。
- 求 30 次至少一次稀有奖的概率时，在上述状态转移的「惊喜返回 0」边乘以该稀有奖未发生的条件概率，再用 `1-Σd_no_rare`；不要使用独立日近似公式冒充精确概率。
- 实施使用已确认 v2 的状态转移、奖励权重、规则版本和对应验收；旧 v1 概率表只保留为对照，不得混用。

本轮确认算法、同步文档并补充性能设计，未修改业务源码或部署，也不改变用户已确定的福利余额独立、手动兑换、悬念文案和兑换区布局。
