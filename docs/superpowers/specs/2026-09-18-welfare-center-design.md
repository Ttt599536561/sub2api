**本轮交付：交互原型、奖励算法、开发计划。尚未开发或启用任何业务功能。** 核心奖励规则已经用户确认，视觉设计和下文标明的默认方案供审阅。竞品截图仅用于了解信息布局，其门槛、套餐兑换、限时活动和条款不作为本项目要求。

签到按钮下方使用「今日惊喜，签到揭晓」，不显示每日金额上下限或原「每天随机…连续奖励额外叠加」提示。活动规则同样不预告每日金额范围，但说明多次未获惊喜时后续机会提高的保护机制，不能宣称日奖独立同分布。签到成功结果和历史记录继续展示已到账金额，抽奖奖池与概率展示不受影响。

## 1. 已确认需求

1. 用户侧栏「充值与订阅」后立即增加「福利中心」，进入独立页面 `/welfare`。
2. 顶部显示福利余额、剩余抽奖次数、累计签到天数；另显示本轮连续签到天数，不能用连续天数冒充总天数。
3. 每个业务日期可签到一次，日奖采用已确认 v2：内部范围 $0.01–$1.00，长期 85.5% 位于 $0.02–$0.20；最多连续 3 次普通日奖，第 4 次成功签到必有惊喜日奖。具体金额范围不提前对用户展示。
4. 连续第 7 / 15 / 30 天，**在当天随机奖励之外**分别额外奖励 $0.60 / $2 / $5（内部规则）。同一天只计一次签到；领取前向用户显示「神秘奖励」，到账后才在成功结果与本人历史流水中披露实际金额。
5. 30 天为一轮；完成第 30 天后的下一次连续签到开启下一轮第 1 天。断签重置本轮进度，无补签。已获福利、累计签到天数不清零。
6. 功能上线后的 API 调用实际账户余额扣款，每累计满 $50，**即刻**获得一次免费抽奖，余数累积。一笔扣款跨过多个 $50，发相应多个次数。
7. 抽奖奖项为 $0.50 / $1 / $2 / $5 / $10 / $20 / $50；用户确认是「至少 70% 不高于 $5，优先控制成本」，无需精确 70%。
8. 每日奖励、连续奖励、抽奖奖励先进入独立福利余额；用户手动兑换后才进入账户余额。
9. 福利余额按 1:1 兑换账户余额，无额外金额门槛；可部分兑换或全部兑换，金额精确到 $0.01。
10. 提供福利记录和日期范围筛选，类型为：全部类型、每日签到、连续签到奖励、抽奖、兑换余额。展示时间、类型、说明、金额变动，以及累计抽奖次数。

## 2. 设计选择

### 推荐：一个页面完成主要操作

- 顶部三张数据卡，余额卡稍宽；「兑换余额」常驻于免费抽奖卡片内的奖池下方，形成独立的「福利兑换」区。用细分隔线、可兑换余额和整行按钮明确区分抽奖与兑换；手机端保持相同顺序。
- 中部左侧每日签到、右侧免费抽奖，各自只有一个主操作按钮。
- 下方直接展示可筛选的福利记录，不需要额外跳页。
- 次要规则收进「活动规则」，概率放在「奖项概率」，首次进入不会被大段文字占满。
- 兑换用弹窗，显示福利余额、金额输入、全部兑换、兑换比例和兑换后账户余额。入口在奖池下方长期显示，操作资格完全独立于签到和抽奖，即使抽奖次数为 0，有福利余额即可直接兑换；中奖弹窗里的「去兑换余额」仅为额外快捷入口。

备选一为「签到 / 抽奖 / 记录」三个标签页，首屏更短，但账户信息和操作关联被拆散，记录查看多一次点击。备选二为沿用竞品纵向大卡片和 30 个连续天数格子，开发最直接，但页面较长，容易把轮次第几天误认为日历日期。首版采用推荐方案。

### 视觉与布局

- 沿用项目青绿色主题（`primary-600 #0d9488`），灰白底、白卡片、细边框、14–16px 圆角，适配现有暗色主题。
- 不使用大面积强蓝背景、网格背景、大转盘、金币动效或闪烁中奖效果。
- 金额使用等宽数字特性；主要信息留足间距，次要文案控制为一行。
- 顶部总天数标为「累计签到」，本轮进度标为「本轮连续」，清晰区分。
- 真实年月日历按周一到周日排列。已签到格显示勾号和当天**每日奖励**；日历下方保留里程碑进度卡，连续奖励的实际到账金额在成功结果与本人流水中展示，不重复统计。
- 7 / 15 / 30 天进度卡保持原布局，只展示天数、「神秘奖励」及未达成／已获得状态，不提前显示现金金额；已获得状态也不附带未来档位金额。卡片与日历月份分开，跨月连续签到正常累计，不按自然月重置。
- 抽奖区域使用次数、到下一次的消费进度、七个静态奖项；点击后展示真实服务端结果。
- 抽奖卡片下方利用原有留白放福利兑换。兑换按钮与抽奖按钮等宽，以低饱和青绿底和细描边区分两个操作；兑换金额右对齐，随签到、中奖和兑换同步更新。页头只保留活动规则，不再放兑换按钮。
- 窄屏上下排列；顶部福利余额占整行，次数和签到天数并排；福利流水改为易读的记录行。

### 原型可演示内容

原型使用固定示例数据（2026-09-18），与真实用户账户完全隔离。可以体验：

- 签到：第 6 → 7 天，累计 23 → 24 天，随机日奖示例 $0.08 + 连续奖励 $0.60，福利余额 $2.80 → $3.48，新增两条流水。
- 抽奖：扣一次机会、增加示例奖金、更新福利余额和记录，展示结果弹窗。
- 兑换：输入金额／全部兑换、金额校验、确认转账、更新福利余额和账户余额示例。
- 记录：类型筛选、日期筛选、空态、错误日期、分页。
- 活动规则、概率说明、上个月日历、键盘关闭弹窗。

原型抽奖结果是固定演示序列，**不代表实际概率采样**。生产随机算法详见配套算法文档。

## 3. 建议默认规则

以下是为使开发方案完整而提出的默认值，不冒充已由用户逐项确认：

| 项目 | 建议默认 | 原因 |
|---|---|---|
| 业务时区 | 固定 `Asia/Shanghai`，00:00 换日 | 避免浏览器、服务器时区和用户切换时区影响签到 |
| 福利余额、抽奖次数期限 | 首版不设置过期 | 用户没有要求过期；避免额外回收逻辑 |
| 签到资格 | 已登录、有效的正常账户 | 不引入竞品「必须先有 API 调用」或付费门槛 |
| 管理员个人账户 | 与普通用户使用同一套福利规则 | 当前个人导航由同一工厂生成，福利按账户计 |
| 简易／后台模式 | 沿用现有个人功能权限限制 | simple 模式不走正常扣款，不能制造虚假消费 |
| 历史消费 | 不回溯；以实际结算时间是否到达 `launch_at` 为界 | 已由用户确认只计算上线后实际扣款 |
| 福利兑换后的再消费 | 计入真实 API 消费 | 当前账户余额没有资金来源分桶；符合用户确认的实际扣款口径 |
| 已结算透支扣款 | 按已提交实际扣款计入 | 现有计费允许已完成请求透支；若排除须另定规则 |
| 兑换统计 | 不增加充值总额，不触发邀请返利 | 福利转余额不是外部资金充值，避免重复发奖 |
| API 费用退款 | 回退消费资格，已用机会形成待抵扣次数 | 保持历史可审计，避免直接追回已兑换奖励 |

消费日、签到轮次互不影响：过月、断签、完成 30 天都不会清空消费余数、抽奖次数或福利余额。

## 4. 已确认的签到 v2 与成本

日奖先依据 `daily_low_count`（连续普通日奖次数，0–3）选择分支，再抽取分支内金额：

| 抽取前 daily_low_count | 惊喜概率 | 普通概率 |
|---:|---:|---:|
| 0 | 20% | 80% |
| 1 | 30% | 70% |
| 2 | 50% | 50% |
| 3 | 100% | 0% |

普通日奖：$0.01 占该分支 2%，$0.02–$0.09 合计 98% 且每分等概率；用 400 权重实现（1 分权重 8，2–9 分各 49），分支期望 $0.0541。惊喜日奖：$0.10–$0.20／$0.21–$0.35／$0.36–$0.50／$0.51–$1.00 的条件概率分别为 65%／25%／9%／1%，区间内每分等概率，分支期望 $0.21375。

惊喜后计数归零，普通后加一。`daily_low_count` 跨漏签、月份和 30 天轮次持续保存，只看随机日奖，不受当天固定里程碑加奖影响；原 `cycle_day` 仍在漏签或完成一轮后重新计数。保证针对任意连续 4 次成功签到，不对漏签者承诺 4 个自然日。

长期平均每 2.64 次签到一次惊喜，日奖期望约 $0.11457348485；新用户状态 0 起首 30 次日奖期望 $3.4012505355，不能按 30 个独立样本计算。消费抽奖继续使用下表，不引入签到保底：

| 抽奖奖项 | 概率 |
|---|---:|
| $0.50 | 45% |
| $1 | 30% |
| $2 | 18% |
| $5 | 5% |
| $10 | 1.5% |
| $20 | 0.4% |
| $50 | 0.1% |

不超过 $5 为 98%，高于 $5 为 2%，单次期望 $1.415。相对于每 $50 实际消费，抽奖名义返奖率为 2.83%。概率描述的是每次独立抽取的长期比例，不保证任意一批用户精确满足该占比。

**首 30 天满勤期望为 $11.0012505355／人：日奖 $3.4012505355 + 固定连续奖励 $7.60。** 1,000／10,000 个首次满勤用户期望发放 $11,001.25／$110,012.51，均不含抽奖。长期稳态每完整 30 天约 $11.0372045455／人；保护计数不随轮次清零，不能把首轮均值直接当作以后每轮均值。首轮理论范围为 $8.53–$37.60，期望不是硬预算上限。

原 v1 仅作对照：日奖期望 $0.07575，完整 30 天期望 $9.87250；v2 首轮总面值增加约 11.43%，长期增加约 11.80%。这些金额是站内余额面值，不是供应商实际现金成本。算法、精确权重、状态递推、退款与循环消费成本详见[奖励算法与成本](2026-09-18-welfare-reward-algorithms.md)及[已确认 v2 说明](2026-09-19-welfare-reward-v2-proposal.md)。

## 6. 数据结构与一致性

### 新增独立福利域

建议新增以下表，账户余额原字段继续承担实际 API 计费职责：

| 表 | 主要字段／职责 |
|---|---|
| `welfare_programs` | 活动批次、固定 `launch_at`、timezone、规则版本、不可变奖表快照、开放状态 |
| `welfare_wallets` | `user_id` 主键；`balance_cents BIGINT`；累计获赠／兑换；`total_checkin_days`；`cycle_id`、`cycle_day`、`last_checkin_date`；`daily_low_count`（0–3，默认 0，跨漏签／轮次保留）；`eligible_spend NUMERIC(20,8)`；`draws_used`；`wallet_version`、`welfare_balance_version` |
| `welfare_checkins` | 用户、业务日期、周期、轮内天数、日奖／连续奖励分数、规则版本、签到操作 ID；唯一 `(user_id,business_date)` |
| `welfare_operations` | 签到／抽奖／兑换幂等键、请求摘要、结果 JSON、规则版本及内部随机值；唯一 `(user_id,operation_type,idempotency_key)`；签到键由服务端用业务日期确定 |
| `welfare_ledger` | 用户、操作引用、类型、金额变化分、变化后福利余额分、说明、轮次／抽奖序号、时间；只追加 |
| `welfare_spend_events` | 结算事实／退款事实、原始唯一来源、用户、实际金额、关联原事件、结算时间、资格变化；同扣费事务写入，不作为延迟发券队列 |
| `welfare_balance_outbox` | 兑换／API费用退款后的两类缓存失效事件、版本／尝试次数、下次重试时间、完成状态 |

`balance_cents` 是需求中的新增福利余额字段，放在用户一对一福利钱包中，避免混入原有 API 余额。签到奖励、抽奖奖励与兑换均是整数分；消费进度必须维持 8 位小数。API 中所有金额使用十进制字符串，不能在 JavaScript 里用浮点金额计算实际转账。

同一次签到可能写两条财务流水，但只增加一天。抽奖记录每次一条，兑换记录为负金额；所有记录有不可变关联操作，重试不能重复发奖。所有改变钱包余额、签到状态、消费进度或已用次数的事务都将 `wallet_version` 加一，用于前端响应先后顺序控制；仅福利余额变化才递增 `welfare_balance_version`，用于兑换报价校验。纯 API 消费累计不使兑换报价过期。

### 为什么用同步资格累计

用户明确要求「即刻获得抽奖」，因此首版选择在现有扣费 SQL 事务里同步更新福利钱包和消费事件。该事务成功即表示次数已增加；下一次概览读取即可看到，无定时扫描或数秒延迟 worker。

成本是每个合格结算多一次消费事件写入和钱包更新，同一用户会在钱包行锁上串行。现有扣费已经在 `users` 行上串行，新增逻辑应保持简短且无外部网络调用，并以并发性能验收决定是否可上线。若未来改为异步，必须重新取得对“即刻”语义变更的认可，不能默默替换。

所有双钱包操作的加锁顺序为 **users → welfare_wallets**，计费、兑换、退款一致。签到和抽奖只锁福利钱包，不能在锁钱包后反向锁 users。读取用户状态可在获取钱包锁前完成，外键初始化也按顺序处理。

### 四个原子操作

1. **签到**：确定服务端日期 → 锁钱包 → 检查当日唯一记录 → 分别读取周期日与 `daily_low_count` → 按 v2 状态采样日奖并确定下一计数 → 算额外奖励 → 入福利余额 → 同事务保存计数、签到和一／两条流水 → 提交。重复签到返回已存在结果，不推进计数；私有审计记录前后计数和各步随机值。
2. **消费累计**：现有计费幂等检查 → 实际扣余额或 capture → 写唯一消费事实 → 累加净合格消费 → 更新资格 → 一起提交。任何回滚不产生次数。
3. **抽奖**：校验幂等 → 锁钱包 → 确认可用次数 → 服务器采样 → 增加已使用次数和福利余额 → 保存操作结果和流水 → 提交。客户端只展示服务端保存的结果。
4. **兑换**：幂等校验 → users 与钱包按序加锁 → 校验金额／快照 → 福利余额扣减、账户余额增加 → 写兑换流水及缓存 outbox → 提交。返回真实两种余额，提交后立即尝试双缓存失效，失败后台可靠重试。

抽奖或兑换网络超时时，客户端保持原幂等键查询／重试，不能制造第二次扣次数或转账。「全部」先由服务端报价，返回金额与 `welfare_balance_version`；最终确认携带该余额版本，若福利余额变化则提示刷新确认，不擅自扩大用户看到的兑换金额。主账户预计余额仅供预览，兑换响应以提交后的真实余额为准。

现有 `InvalidateAuthCacheByUserID` 不返回失败结果，不能用它的正常返回来确认 outbox 已成功。即时失效可沿用；可靠 worker 须调用可返回 error 的删键／跨实例广播方法，两类失效均完成才确认事件。现有余额缓存没有可直接复用的版本保护，计划新增用户资金缓存 generation 栅栏：读 DB 前记 generation，回填时用原子 CAS 比较，失效先递增 generation 再删键；不允许旧 DB 读在兑换／退款后回填旧余额。对包含余额快照的认证缓存同样验证这条竞态，不把删除缓存一次当作一致性证明。

### 资格公式与退款

令 `S` 为上线后净合格消费，`E=floor(max(S,0)/50)`，`U` 为已完成抽奖次数。

- 可用次数 `max(E-U,0)`；待抵扣次数 `max(U-E,0)`。
- 正常情况下到下次门槛的差额为 `50-(S mod 50)`，刚满门槛后下一次需再消费 $50。
- 若退款导致已用次数高于可获次数，下一个可用次数的目标消费为 `50 × (U+1)`，前端应显示待抵扣状态，不能错误宣称仅需补到下个整 $50。
- 退款必须关联原合格消费，账户退款与消费回退同事务；不把充值退款、管理员加余额或冻结释放混为 API 消费退款。
- 已抽奖励首版建议保留，未来消费先抵扣次数欠额；不删除旧记录，不自动追回账户余额。此为异常处理提案。

## 7. 用户 API 提案

前缀 `/api/v1/user/welfare`；所有 user_id 从 JWT subject 提取。

| 方法／路径 | 作用 | 核心字段 |
|---|---|---|
| GET `/overview` | 一致性读取钱包、活动和机会 | `welfare_balance`、`account_balance`、`available_draws`、`draws_used`、`total_checkin_days`、`cycle_day`、`today_checked_in`、`business_date`、`next_reset_at`、`eligible_spend`、`next_draw_remaining`、`ticket_debt`、`wallet_version`、`rules_version`；里程碑仅含 `day`、`label:神秘奖励`、`status` |
| GET `/calendar?month=2026-09` | 当前用户月度签到 | `business_date`、已到账 `daily_reward`、`cycle_day`；不附带连续奖励金额预告或规则表 |
| POST `/check-in` | 当日签到 | 空业务请求体；响应日奖、额外奖励、新钱包快照、`already_checked_in` |
| POST `/draw` | 使用一次机会 | `Idempotency-Key`；响应奖项、奖励、新次数、福利余额、操作 ID |
| POST `/redemption-quote` | 部分／全部兑换预览 | `mode:partial/all`，部分包含金额字符串；返回金额、`welfare_balance_version`、两种预计余额，不转账 |
| POST `/redeem` | 确认兑换 | `Idempotency-Key`、`amount`、`welfare_balance_version`；返回真实账户／福利余额、两种版本和操作 ID |
| GET `/operations/:id` | 查询自己操作结果 | 返回 committed 结果或明确未找到；越权不可读 |
| GET `/records?type=all&date_from=...&date_to=...&page=1&page_size=20` | 福利财务流水 | type 仅四类+all，时间、类型、说明、金额、操作 ID、剩余福利余额；稳定排序及分页 |
| GET `/rules` | 当前生效的用户规则 | 抽奖奖项概率、每日签到领取说明、里程碑 `day` 与 `label:神秘奖励`、时区、生效时间、版本；不返回每日金额范围、里程碑金额或内部预算 |

公开活动规则和用户规则／概览 DTO 使用明确白名单，不能直接序列化服务端完整奖表。签到奖励只在成功提交的本人签到／操作结果和本人财务流水中返回已到账金额，不夹带未来奖励金额及每日金额范围。不得把未公开规则金额放进前端常量、i18n、SSR 数据、隐藏 DOM、tooltip、ARIA 属性或网络响应后再用 CSS 隐藏；抽奖的公开奖项和概率保持原样。

记录日期以活动时区转成 UTC 半开区间 `[开始日00:00, 结束日次日00:00)`。拒绝逆序日期、未知类型、负页码；限制 page_size 最大 100。索引采用 `(user_id,created_at DESC,id DESC)` 与 `(user_id,type,created_at DESC,id DESC)`。

幂等键相同且请求摘要不同返回 409；兑换的 `welfare_balance_version` 过期返回 409 并附新报价指引，不因消费导致的 `wallet_version` 变化拒绝兑换；金额零、负数、超两位小数、超余额拒绝；抽奖无次数返回明确业务错误且不调用随机源。业务错误码由新 welfare 域统一映射到现有错误响应规范。

## 8. 交互状态与边界

- 数据未就绪：骨架与按钮禁用；不能先显示 0 再闪成真实余额。
- 请求处理中：操作按钮禁用，防重复点击；失败重试保持幂等键。
- 已签到：当天禁用按钮，展示实际到账总额；不能前端乐观随机发金额。
- 连续奖励达到当天自动到账，不额外要求点击「领取礼包」。
- 今日已签到但重新打开页面：以服务器返回状态显示；跨北京时间午夜／重新回到页面刷新。
- 抽奖结果弹窗里展示「已存入福利余额」与「去兑换余额」，无需转盘。
- 福利余额为 0：兑换入口可解释无可兑换余额，确认按钮不可用。
- 兑换提交成功但余额刷新失败：显示兑换成功并提示同步，不能当作转账失败再提交新操作。
- 本轮中断：显示「本轮连续 0 天，今天签到从第 1 天开始」，旧 calendar 保留已签到日。不能只显示数据库里陈旧 cycle_day。
- 账号切换／退出：销毁福利状态并丢弃上个会话的晚到响应。
- 弹窗键盘焦点约束、Esc 关闭、读屏结果提示；手机按钮触控区域足够。
- 关闭获奖开关建议只停签到、抽奖和新增消费资格，保留已有余额兑换与流水访问；已有权益不因停活动消失。区分 UI 可访问与发奖开放状态，避免单一隐藏菜单导致余额无法兑换。

## 9. 上线与验收范围

首版不做礼包订阅时长兑换、补签、积分商城、付费抽奖、多连抽、排行榜、分享裂变、提现或兑换门槛。运营只需活动开关、生效时间、规则版本与成本数据，复杂可视化运营后台不作为本次用户页面的前置条件。

上线前必须具备并发幂等、精度边界、费用来源排除、兑换账务守恒、缓存失效重试、会话隔离测试，以及里程碑金额不提前泄露的 API／前端测试。验证未领取与部分已领取状态的 rules／overview 响应、页面及隐藏属性均无未来档位金额，成功结果与本人流水准确披露已到账金额。既有单笔计费 fallback 和 `UsageService.Create` 旁路需明确收口，不能因为主路径正确就宣称所有消费均已覆盖。

部署策略：先增加兼容表和设置且发奖关闭；完成迁移和集成验证后，设置实际 `launch_at` 再开放功能。回滚时保留权益表与已发福利，不回退／删除资金记录。上线成本预警只用于运营提示，不暗中调低单个用户的中奖概率。

具体任务与验收命令见 [开发计划](../plans/2026-09-18-welfare-center.md)。
