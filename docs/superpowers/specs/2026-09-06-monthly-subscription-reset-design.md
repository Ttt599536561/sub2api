## 1. 目标

在用户已购买的月卡订阅卡片上增加“重置”按钮和“自动重置日额度”开关。每次成功重置，以减少 24 小时有效期为代价，把该订阅当前每日已用额度清零；日额度上限保持对应月卡分组的配置。保留现有自然刷新、周/月用量及历史消费记录。

月卡使用独立分组，因此通过管理员指定的月卡分组控制功能资格，不根据套餐名称、当前剩余天数或购买价格识别月卡。

## 2. 已确认的需求

| 编号 | 规则 |
| --- | --- |
| R01 | 仅月卡开放；月卡为独立订阅分组。周卡、季卡等其他分组不开放。 |
| R02 | 已购和新购月卡都支持。月卡续费或提前扣减天数不改变其月卡资格。 |
| R03 | 每份订阅分别保存自动开关、成功重置次数；不同订阅独立计算。同一订阅的多把 API Key 共享该订阅用量和次数。 |
| R04 | 手动重置只要求当前每日已用额度大于 0，不必用满。不弹确认框，点击后直接执行。 |
| R05 | 自动重置仅在当前每日已用额度达到或超过该分组每日上限时触发。用户开启后立即检查，后续由服务端处理，不依赖网页保持打开。 |
| R06 | 手动和自动允许同时使用，但同一轮额度不能因并发触发而重复扣天数。 |
| R07 | 每次成功只扣 24 小时；扣后到期时间必须严格晚于服务端判定时间。剩余时间小于或等于 24 小时均禁止重置。 |
| R08 | 不把最后一天强制扣成 0 天；保留剩余有效期和原有到期行为。不允许出现负剩余时间的成功扣减。 |
| R09 | 每张月卡每个系统时区自然日，手动加自动最多成功重置 100 次。失败、重复请求、自然刷新不占次数。 |
| R10 | 成功后每日已用额度为 0；不保留未用完额度，不叠加额度，也不做超额结转。 |
| R11 | 每日上限由后端根据目标订阅对应分组读取。A 卡上限 100，B 卡上限 200，不能串用。 |
| R12 | 只重置每日用量，保留每周/月累计用量及其原有额度限制。 |
| R13 | 保留现有按系统时区凌晨 0 点自然刷新日用量的行为；自然刷新不产生本功能的扣天事件或成功次数。 |
| R14 | 已有月卡上线时保持原有效期和用量；自动重置默认关闭，只有用户主动开启后才允许自动扣天。 |
| R15 | 保留消费记录和现有结算口径。重置事务前已结算的日用量被清零，重置后才结算的请求计入重置后的每日用量。无需等待所有在途请求结束。 |
| R16 | 未到期月卡续费保留原自动开关，原来开启仍开启，原来关闭仍关闭；过期后重新开通默认关闭。到期时间等于服务端当前时间也按已到期处理。 |
| R17 | 自动重置因当天次数达到上限或剩余有效期不足而暂停时，保留用户的开启状态，条件恢复后自动继续检查。页面不额外显示暂停原因，保留开关、N/100 次数及原有到期时间展示。过期后重开仍执行 R16 的默认关闭规则。 |
| R18 | 管理员修改月卡分组的每日上限后，已有月卡后续重置采用当前新上限；自动耗尽判断也采用当前上限。重置事件记录当次上限快照，其他月卡分组及历史消费记录不变。 |
| R19 | 当前有效周额度或月额度达到或超过上限时，手动和自动均禁止提前重置，不扣天、不计次数。手动重置按钮置灰且不可点击；后端仍独立校验，不能绕过页面限制。 |

周/月窗口已自然到期时，先按原有规则维护窗口，再判断是否耗尽。未配置的周/月上限不构成额外限制。

### 2.1 示例

| 日上限 | 重置前已用 | 触发方式 | 其他条件满足时的结果 |
| --- | ---: | --- | --- |
| 100 | 0 | 手动 | 拒绝，不扣天、不计次数 |
| 100 | 60 | 手动 | 已用变为 0，上限仍 100；减少 24 小时，计 1 次；剩余的 40 不叠加 |
| 100 | 60 | 自动 | 不触发 |
| 100 | 100 | 手动或自动 | 已用变为 0，上限仍 100；减少 24 小时，计 1 次 |
| 100 | 100.3 | 手动或自动 | 已用变为 0，不结转 0.3；周/月仍保留实际消费 |
| 200 | 200 | 手动或自动 | 仅该卡清零，上限仍 200；其他月卡不变 |

刚开通的 30 天、日上限 100 的卡，在同一天连续使用、不续费、不跨自然刷新且不考虑请求超额时，初始一轮加最多 29 次提前重置，可使用 30 轮额度。最后保留不足或等于 24 小时的有效期，不再提前重置。这不是对所有购买时刻、跨日场景总可用额度的重新定义，既有午夜刷新仍然生效。

## 5. 技术方案选择

| 方案 | 评价 |
| --- | --- |
| 顺序调用现有“管理员清零”和“缩短一天”接口 | 不采用。两个动作不是同一事务，缺少用户归属、轮次和次数保护，可能只成功一半。 |
| 新增原子提前重置能力，沿用现有到期时间和日用量 | 推荐。符合已确认规则，新增分组许可、订阅偏好/计数/版本和事件表，复用现有业务链。 |
| 改为独立天数钱包，允许扣到 0 天后继续使用 | 不采用。最后一天已经确认不再提前重置，无需重构订阅权益模型。 |

以下是推荐方案的设计草案。正式开发前应完成并发方案评审和文档确认。

## 6. 数据库设计

使用新增的 forward-only SQL 迁移，同时同步 Ent Schema 和生成代码。此文档不指定迁移序号，实施时按当时主线确定，禁止改动历史迁移。

### 6.1 分组许可

在 `groups` 增加 `allow_subscription_day_reset`，布尔值，默认 `false`。仅对 `subscription_type=subscription` 且日上限为正数的分组允许开启。管理员选择已知的月卡独立分组启用，不自动按名字或剩余时间批量推断。

上线后，开启某个月卡分组即覆盖该分组已有和新购订阅。关闭后，新的手动和自动重置均被后端拒绝，但不撤销此前合法扣减或恢复的额度。

### 6.2 订阅状态

在 `user_subscriptions` 建议增加：

| 字段 | 用途与约束 |
| --- | --- |
| `auto_daily_reset_enabled` | 用户偏好，布尔值，默认 `false` |
| `daily_reset_version` | 独立递增版本，默认 0，不允许负数；用于区分同日不同额度轮次和拒绝旧操作。日用量重置、有效期相关变更及用户自动偏好变更时递增，普通消费累加不递增 |
| `preserve_calendar_daily_reset` | 默认 `false`；首次提前重置前，若原订阅遵循日历日刷新，则在同一事务中设为 `true`，避免缩短有效期后被误判为一日卡 |

`preserve_calendar_daily_reset` 表示保留原有刷新行为，不是额外赠送额度的开关。其生效不依赖分组是否继续允许提前重置。有效期内续费保留；过期后重新开通新周期时，按新周期原本的语义重新初始化。现有真实一日卡不因本功能获得跨午夜刷新资格。

不新增可被独立修改的 `remaining_days` 字段，避免它与 `expires_at` 发生分歧。扣减使用准确时间，不使用页面取整后的“剩余天数”。今日成功次数从下一节的事件表统计，不再额外保存一份订阅计数。

### 6.3 重置事件

新增 `subscription_daily_reset_events` 表，保存成功扣天事件：

- 事件 ID、订阅 ID、用户 ID、分组 ID、来源 `manual` 或 `automatic`。
- 操作 ID、请求指纹、重置前后版本、系统时区名称、计数日期及成功后的当日序号。
- 重置前每日用量、重置后每日用量 0、该次日上限快照。
- 扣减前后到期时间、扣减秒数 86400、服务端决策时间。

数据库唯一约束覆盖“订阅 + 操作 ID”“订阅 + 重置前版本”和“订阅 + 计数日期 + 当日序号”。在订阅行锁下，通过有索引的订阅 ID 与计数日期统计已提交成功事件，下一序号为当前次数加 1。序号数据库约束为 1 到 100，因此即使业务判断有遗漏，也不能插入第 101 个不同序号的当日成功事件。

金额使用现有 NUMERIC 精度及金额规范化方式，不能用前端两位小数决定是否消耗过或是否耗尽。日用量必须为有限非负值，日上限必须为有限正值；NaN、Infinity 或负用量等异常数据拒绝操作并记录故障，不把异常值当成耗尽信号。

事件约束要求扣减恰好 86400 秒、扣减后到期时间晚于本次决策时间、次数在 1 到 100 之间。业务谓词仍需在事务内校验；不能通过把负数显示成 0 来代替真实保护。

事件与订阅修改在同一事务提交。失败不写成功事件。订阅软删除后仍保留审计关联；流水不保存 API Key 明文或请求提示词。本版不自动清理重置事件，保留追溯和操作重放依据；未来增加清理必须单独定义幂等保留期及归档规则。

## 7. 原子重置流程

1. 根据登录身份确定用户，校验目标订阅归属；普通用户不得传入另一个用户 ID 或指定恢复金额、扣减天数、次数。
2. 在事务中按固定顺序取得分组共享锁、订阅行锁，重新核对归属。所有新入口使用同一顺序；与现有续费/管理修改交互时检查是否存在反向加锁。
3. 锁内查询该操作 ID 的既有成功事件；同一参数回放既有结果，不产生新的扣减，同一 ID 对应不同参数返回冲突。重放已经成功的结果不要求订阅当前仍满足新重置条件。事件只能和实际扣减一起提交，不能靠事务外 HTTP 幂等缓存保证不重复扣天。
4. 对新的操作，在获得锁后取得一次数据库当前时间，检查状态、当前分组许可、正数日限额。用户、分组或订阅停用/删除均不能执行。
5. 按既有日/周/月规则先完成已到期窗口的维护。自然维护成功不代表发生了一次付费提前重置，也不扣天数。
6. 校验客户端观察到的额度轮次/日期。若自然刷新、另一个重置、续费或管理员操作已改变相关状态，返回新的状态并要求刷新，禁止把旧按钮操作套用到新一轮额度。
7. 判断剩余时长严格大于 24 小时；锁内统计今日成功事件，要求小于 100；按 R19 判断有效周/月额度没有耗尽。
8. 手动要求数据库日用量大于 0；自动还要求用户开关当前为开且日用量大于或等于当前日上限。
9. 在一次更新中把每日已用额度设为 0、日窗口锚定今天 0 点、到期时间减少 24 小时、重置版本递增，并保留原日历日刷新语义。
10. 同事务写入带下一当日序号的成功事件并提交，今日成功次数因此增加 1；随后失效相关缓存、返回数据库最新订阅状态。

自然日变化后按新的日期查询事件，今日次数自然从 0 开始，无需新增每天遍历所有订阅清零计数的任务。所有服务实例必须使用一致的系统时区；运行期间改变系统时区不属于本功能，需维护窗口内另行处理计数日期的兼容。

自然刷新与提前重置必须共享同一订阅行的串行化边界：若锁内决策时已跨午夜，先自然刷新，再判断是否还有可提前清零的用量；若事务决策在午夜前，提前重置记在前一日，后续午夜刷新按原规则进行。每次调用固定使用同一决策时间，不能在一笔操作中混用两天的日期。业务性拒绝提前重置时，可以提交本来就应该发生的自然维护，但不写提前重置事件；数据库技术错误则回滚整个事务。

### 7.1 其他订阅写入路径

需要检查管理员缩短/延长、续费、撤销、恢复、暂停、重置用量及窗口维护。涉及到期时间或额度轮次的操作，必须在同一订阅锁下基于新状态更新，并维护版本，避免旧快照覆盖提前扣减。管理员原有重置权限和业务效果不改，但其操作不得删除本功能当天成功事件来清掉次数。

消费结算仍原子累加日/周/月并沿用请求去重。按数据库事务串行化顺序决定归属：在提前重置之前提交的日用量被清零；之后提交的日用量累加到新的日用量。周/月与历史日志不因提前重置而减掉。这是已确认的 R15，不增加“按请求开始时刻回溯扣到旧轮次”的机制。

## 8. 自动重置与故障恢复

自动、手动必须共用第 7 节的原子能力，不分别实现扣天数算法。

- 开启开关：先持久化用户偏好并推进版本，再立即进行一次资格检查；已耗尽则尝试重置，未耗尽则等待消费结算。开关设值必须携带观察到的版本，迟到的旧开启请求不能覆盖用户后来提交的关闭操作。
- 消费结算后：在扣费已经提交后触发一次检查。不得因为自动重置失败而撤销已经发生的消费记录。
- 请求准入：遇到日额度耗尽且用户开启自动重置时，调用公共检查并最多重新判断一次，不做无限重试。
- 恢复扫描：服务启动及周期性扫描数据库中开启开关、有效且可能耗尽的订阅。建议 30 秒一次、分批和有界并发；用于补偿进程退出、触发丢失或临时数据库故障。
- 关闭网页不影响执行。后台任务每次进入锁内重新读取开关；用户关闭后尚未进入临界区的旧任务不得继续扣天。
- 同一批重复通知的旧版本只能成功一次。重置后若又有新的实际消费达到上限，可再次合法触发，直至次数或有效期耗尽。

正常环境下，开启时在该次操作内完成检查；用量结算触发的重置以秒级完成为设计目标。故障恢复不承诺绝对实时，在页面展示实际状态，不伪造“已经重置”。周期、并发数和超时应在实施验证后确定为配置默认值。

若设置保存成功但即时重置发生技术错误，响应必须分别描述“开关已开启”和“本次尚未重置”。不得把开关写成功说成失败，也不得因客户端重试再扣一天。

## 9. 缓存与一致性边界

已确认旧实现存在订阅 L1 缓存、Redis 快照和异步用量增量。单纯删除缓存不够：旧查询可能稍后回填旧有效期，延迟增量可能污染重置后的缓存。

本版建议采用正确性优先的方案：

1. 提前重置、自动触发和用户可操作状态只依据数据库新快照，绝不依据 Redis 的旧日用量直接扣天。
2. 订阅请求入口通过数据库读取当前分组许可及订阅状态，避免用旧 API Key 内嵌分组配置决定是否启用新校验。对启用本功能的月卡，额度和到期的最终准入使用数据库快照；排队后必须重新校验。
3. 对这些月卡停止把旧 Redis 增量缓存作为权威额度来源；重置后仍清理 L1/Redis 并复用已有跨实例失效通知。清缓存失败不能把已经提交的重置当成失败重新执行。
4. 功能组被关闭时，清理受影响缓存；曾经发生过提前重置的订阅继续使用数据库准入。是否存在历史事件可通过订阅 ID 索引查询，不能仅因为关闭分组开关就马上重新信任旧缓存。
5. 数据库不可用时拒绝需要权威状态的重置和新请求，不用过期缓存猜测可扣天数。已完成的重置可凭操作 ID 查询其结果。

代价：需要增加订阅准入的数据库读取，必须测量数据库连接池和请求延迟；这是一项明确的设计取舍，未验证前不承诺“完全不影响性能”。如果负载验证不能接受，应在开发前改为经过完整验证的缓存代际隔离方案，而不是去掉权威校验。两套方案不同时实施。

## 10. API 草案

以下端点和字段为设计建议，尚未实现。普通用户端点放在现有 JWT、用户功能守卫和限流中间件下。

| 接口 | 请求与结果 |
| --- | --- |
| `POST /api/v1/subscriptions/:id/reset-daily` | 必须携带 `Idempotency-Key`、预期 `daily_reset_version` 和观察到的系统日期；请求不能携带恢复金额或扣减天数。返回操作 ID、是否重放、最新订阅和重置状态。 |
| `PUT /api/v1/subscriptions/:id/auto-daily-reset` | 携带预期版本设置目标布尔值，不使用“取反”命令；返回持久化偏好、即时检查结果和最新状态。旧版本重试回读状态，不重新覆盖偏好；实际扣天仍由重置事件的操作 ID 和轮次保护。 |
| `GET /api/v1/subscriptions/:id/daily-reset-state` | 返回资格、自动偏好、内部不可执行原因码、当日次数、上限 100、版本、当前额度、服务器时间和到期时间。原因码用于后端判断和排障，不额外渲染为自动暂停提示。 |
| `GET /api/v1/subscriptions/:id/daily-reset-operations/:operationId` | 查询当前用户自己的操作结果，解决提交成功但响应丢失；不存在不代表可以换新操作 ID 盲重试。 |
| 现有管理员分组创建/编辑接口 | 增加 `allow_subscription_day_reset`；管理员复制分组、批量变更及缓存失效一并核对。 |

列表与进度响应增加同源重置状态，避免页面自行用浮点显示值判权。推荐稳定原因码：`RESET_NOT_ALLOWED`、`RESET_NO_USAGE`、`RESET_INSUFFICIENT_VALIDITY`、`RESET_DAILY_COUNT_LIMIT`、`RESET_WEEKLY_LIMIT`、`RESET_MONTHLY_LIMIT`、`RESET_STATE_CHANGED`、`RESET_OPERATION_CONFLICT`。无权限或不属于用户的订阅统一按不存在处理。

手动重置与自动开关操作必须复用请求 ID 直到结果明确。数据库提交结果不确定时返回可查询的操作 ID；不得承诺“网络错误一定没有扣天”。

## 11. 页面与交互

- 修改用户订阅页 `frontend/src/views/user/SubscriptionsView.vue`，在每日用量行添加重置按钮，卡片下方添加自动重置开关和“今日已重置 N/100 次”。
- 仅获准月卡显示控件。其他分组不显示；已过期等不可用月卡按现有列表规则展示状态。
- 手动直接执行，无确认弹窗。请求中仅禁用该卡相关提交控件，不阻塞其他卡。
- 自动重置因次数或有效期受限时，开关仍显示开启；保留 N/100 和原有到期时间，不添加暂停原因文案、原因 tooltip 或自动重复弹出的提示。条件恢复后继续检查，见 R17。
- 手动按钮仍按资格正确禁用；用户主动提交时遇到实际业务失败或网络错误，保留正常错误反馈，这与自动暂停时不额外显示原因区分处理。
- 周额度或月额度耗尽时，手动按钮置灰并设置真实禁用状态，鼠标和键盘均无法提交；自动执行也被后端阻止，但不因此阻止用户关闭自动开关。
- 成功使用服务端返回值立即更新额度、有效期、次数和版本；旧轮询响应不能覆盖新数据。
- 结果不确定时显示“正在核实”，先查询操作结果或同操作 ID 重试；不能自动创建第二个扣天请求。
- 自动开关关闭始终应可操作，不能因为剩余时间不足或周/月耗尽而阻止用户关闭。
- 沿用现有图标、按钮、开关、Toast、表格及中英文规范。移动端与桌面均检查按钮、金额、次数和到期时间不重叠。

## 14. 上线与回退

- 先备份并验证新增迁移，新增字段保持安全默认值：组许可关闭、用户自动关闭、版本为 0、没有成功重置事件所以次数为 0。部署旧数据不能自动缩短有效期。
- 核对实际月卡分组清单，由管理员逐组启用；旧月卡立即获得手动资格，自动仍需用户开启。
- 多实例升级期间先保持许可关闭，所有实例升级后才开启。旧实例不理解新到期语义及缓存策略，不允许在功能启用时混跑。
- 功能有问题时首先关闭组许可，停止新的提前重置；已提交事件和到期时间保留，不直接删字段或回滚历史扣减。
- 已发生扣天后不能直接降回旧二进制，因为旧程序可能重新误判一日卡。需要维护模式下完成兼容检查及经过核对的数据恢复方案。
- 监控成功/拒绝/技术失败、自动检查延迟、计数冲突、缓存失效失败和待核实操作；日志只保留必要标识，不记录密钥。

## 15. 文档当前结论

需要修改数据库及后端、前端相关模块；无需新增天数钱包，不做超额结转。安全重点是事务一致性、同轮次去重、准确时间边界、午夜兼容、旧缓存隔离和旧订阅迁移。

产品规则已逐项确认；技术设计和测试说明等待整体审阅，尚未实施或运行功能测试。缓存读路径的性能取舍需纳入技术设计审阅，之后仍需用户明确授权开发。
