# 福利奖励算法与成本核算

日期：2026-09-18。本文是设计文档，不包含业务代码变更。通用页面、接口、表结构和实施步骤由主设计及实施计划说明；本文只规定概率、金额计算、签到周期、结算一致性与可审计要求。

更新：2026-09-19，用户已确认采用[签到 v2](2026-09-19-welfare-reward-v2-proposal.md)，本文件已同步为当前算法依据；尚未开发或上线，原 v1 仅作明确标记的成本对照。

本文的连续奖励固定金额、完整规则快照与成本数据仅供项目所有者和开发人员内部使用。7／15／30 天里程碑领取前保留悬念，公开呈现为「神秘奖励」；固定连续奖励与消费抽奖分布不变，日奖已采用下述 v2 状态保护算法。

每日签到同样保留悬念：用户页面文案为「今日惊喜，签到揭晓」，公开活动规则和用户 API 不预告每日金额上下限。下述每日范围、概率与期望供内部配置和核算；签到成功及本人历史流水仍返回实际到账金额。用户规则说明多次未获惊喜后机会提高的统一保护机制，不宣称日奖独立同分布；抽奖的公开奖项与概率仍正常展示。

## 1. 规则状态与计量口径

用户已确认：

- 每日签到采用已确认 v2，内部奖励范围 $0.01–$1.00，长期 85.5% 落在 $0.02–$0.20；最多连续 3 次普通日奖，随后一次成功签到保证惊喜日奖。
- 本轮连续第 7、15、30 天，分别在当日日奖之外额外发 $0.60、$2、$5；每轮 30 天，漏签重置，不提供补签。
- 抽奖奖项为 $0.50、$1、$2、$5、$10、$20、$50；至少 70% 的抽奖结果不超过 $5，优先控制成本，大于 $5 的结果应稀有。
- 只累计福利上线后 API 调用实际扣除的账户余额；累计每 $50 获得 1 次抽奖，余数保留。
- 福利余额由用户手动按 1:1 兑换到账户余额。兑换金额以 $0.01 为最小单位，无额外起兑门槛；例如 $0.01 可以兑换。

本文日奖概率与状态转移以用户已确认 v2 为准，消费抽奖维持原 1000 权重奖表。业务日期时区建议 `Asia/Shanghai`；福利余额和抽奖次数建议不过期；退款采用第 7 节建议的净消费资格与次数欠额处理。上述三项默认值尚非用户明确确认的规则，应在主设计中标明。

费用精度与现有账务 `NUMERIC(20,8)` 一致。所有金额 API 字段使用十进制字符串，例如 `"0.01000000"`、`"49.99999999"`，不得经 JSON number 或前端浮点运算完成记账。奖励和兑换以美分为最小单位，但 API 消费累计必须保留 8 位小数。

`NUMERIC(20,8)` 全范围乘以 `10^8` 后最多有 20 位，不能默认全部放入 `int64`。累计消费使用数据库 `NUMERIC` 或任意精度十进制；固定奖项的美分整数可以用 `int64`。

## 2. 已确认 v2：状态保护与日奖分布

`daily_low_count` 保存自上次惊喜日奖后连续普通日奖的成功签到次数，默认 0、范围 0–3；跨漏签、月份和 30 天签到轮次保留。它与 `cycle_day` 独立，只按随机日奖判断，不把额外里程碑奖励计入。

| 抽取前 daily_low_count | 惊喜分支概率 | 普通分支概率 |
|---:|---:|---:|
| 0 | 20% | 80% |
| 1 | 30% | 70% |
| 2 | 50% | 50% |
| 3 | 100% | 0% |

用 `randInt(100) < [20,30,50,100][n]` 决定分支。普通日奖到账后计数加一，惊喜到账后归零；失败及重试不额外推进。任意连续 4 次成功签到至少一次惊喜，每天签到者等价于最多 4 天；漏签者不能按 4 个自然日承诺。

普通分支用 400 整数权重：1 分权重 8，2–9 分各 49，即 $0.01 条件概率 2%、$0.02–$0.09 合计 98%。其精确期望为 `$0.0541`。

惊喜分支先按以下 100 权重选择区间，再在区间闭区间内均匀抽取整数美分：

| 惊喜日奖区间 | 条件权重／概率 | 区间均值 |
|---|---:|---:|
| $0.10–$0.20 | 65／65% | $0.15 |
| $0.21–$0.35 | 25／25% | $0.28 |
| $0.36–$0.50 | 9／9% | $0.43 |
| $0.51–$1.00 | 1／1% | $0.755 |

惊喜分支精确期望为 `0.65×0.15 + 0.25×0.28 + 0.09×0.43 + 0.01×0.755 = $0.21375`。这张表是条件概率，不能直接当所有签到的分布。

相邻惊喜间隔 1／2／3／4 次的概率为 20%／24%／28%／28%，平均 2.64 次；稳态惊喜率 `25/66`，日奖期望 `0.0541 + (0.21375−0.0541)×25/66 = $0.114573484848…`。长期 85.5% 日奖位于 $0.02–$0.20，大于 $0.50 占约 0.37878788%，恰好 $1 占约 0.00757576%。这些是长期比例，不是新用户第一天的固定概率。

初态 `d=(1,0,0,0)`，每次令 `q=Σd[i]p[i]`，再更新 `d'=(q,0.8d[0],0.7d[1],0.5d[2])`。前 30 次 `Σq=11.13843116532944`，日奖期望为 `30×0.0541 + (0.21375−0.0541)×Σq = $3.401250535544845`。状态保护使各日相关，不能按独立抽样计算。

首 30 次至少一次 >$0.50 的概率约 10.58123704%，至少一次恰好 $1 约 0.22253874%；用“尚未命中”状态 DP 求得，不能套独立每日公式。完整推导和上限对照见[已确认 v2](2026-09-19-welfare-reward-v2-proposal.md)。

## 3. 30 天周期、累计签到与额外奖励

`wallet.total_checkin_days` 表示历史累计成功签到天数，漏签和完成 30 天均不清零。`cycle_day` 表示本轮连续签到天数，范围为 1–30；尚未签到时可为 0。二者分别展示，不能通过累计天数直接取模推导当前轮次。

以服务端固定业务时区计算 `today`，以用户当天成功签到唯一约束防止重复：

```text
若 last_checkin_date == today：返回当天已提交结果，不再抽奖或发奖。
否则：
  若 last_checkin_date == today - 1 个日历日 且 cycle_day < 30：
    next_cycle_day = cycle_day + 1
  否则：
    next_cycle_day = 1
  total_checkin_days += 1
  daily_reward, next_low_count = 按本文第 2 节及原 daily_low_count 抽样
  milestone_reward = {7: 0.60, 15: 2.00, 30: 5.00}[next_cycle_day]，缺省 0
  当天总奖励 = daily_reward + milestone_reward
  同事务保存 next_low_count，不因 next_cycle_day=1 而清零
```

日历日比较不能使用固定的 24 小时差代替。完成第 30 天后，下次成功签到开始第 1 天；漏签也从第 1 天重新开始。累计消费、已获得/已使用抽奖次数及福利余额均不随签到周期归零。

例：一直连续签到时，第 30 次显示“累计 30 天，本轮第 30 天”，第 31 次显示“累计 31 天，本轮第 1 天”；中断后再签到，累计天数加一，本轮重新为第 1 天。

里程碑卡片仅显示天数、「神秘奖励」及未达成／已获得状态。公开活动规则和用户 `rules`／`overview` DTO 不包含未到账里程碑金额、完整内部奖励映射或可推导固定奖励的内部预算；已获得状态不附带未来金额。不能在前端硬编码金额或先下发再隐藏。实际连续奖励金额仅在成功到账后的本人操作结果和历史财务流水中披露，便于核账；不对未来档位作现金预告。下表及成本公式属于内部核算，不作为用户规则直接发布。

| 周期节点 | 当日额外奖励 | 本轮截至该日累计固定额外奖励 |
|---|---:|---:|
| 第 7 天 | $0.60 | $0.60 |
| 第 15 天 | $2.00 | $2.60 |
| 第 30 天 | $5.00 | $7.60 |

初始日奖保护状态为 0、完整连续签到首 30 天的期望为：

```text
3.401250535544845 + 0.60 + 2.00 + 5.00
  = 11.001250535544845 美元
```

稳态任意 30 次日奖期望约 $3.4372045455，若同时完成一轮连续签到，合计约 $11.0372045455；不能将初态 0 的首轮期望机械用于后续每轮。首轮每人总奖励范围为 **$8.53–$37.60**：30 次至少有 7 次惊喜，日奖最低合计 $0.93；当日 $1 上限只约束随机日奖，第 30 天连同额外奖励最高 $6。

固定里程碑仍为每完整周期 $7.60，占首轮总期望约 69.08%。原 v1 仅供对照：日奖期望 $0.07575、满勤 30 天 $9.87250；v2 首轮总期望增加约 11.43%，长期约 11.80%，不是成本不变。

## 4. 抽奖分布

一次均匀生成整数 `u ∈ [0, 1000)`，按以下固定表匹配：

| 奖励 | 整数权重 | 概率 | 命中整数范围，含两端 |
|---|---:|---:|---|
| $0.50 | 450 | 45% | 0–449 |
| $1.00 | 300 | 30% | 450–749 |
| $2.00 | 180 | 18% | 750–929 |
| $5.00 | 50 | 5% | 930–979 |
| $10.00 | 15 | 1.5% | 980–994 |
| $20.00 | 4 | 0.4% | 995–998 |
| $50.00 | 1 | 0.1% | 999 |
| 合计 | 1000 | 100% | 0–999 |

- 奖励不超过 $5 的概率为 **98%**，满足至少 70% 的要求；不超过 $2 的概率为 **93%**。
- 大于 $5 的概率为 **2%**，平均每 50 抽出现一次；$50 概率为 **0.1%**，平均每 1000 抽出现一次。平均次数不代表保底或承诺。
- 每抽精确期望为 **$1.415 = 283/200 美元**。

```text
E(抽奖)
  = 0.50 × 0.45 + 1.00 × 0.30 + 2.00 × 0.18
  + 5.00 × 0.05 + 10.00 × 0.015 + 20.00 × 0.004 + 50.00 × 0.001
  = 1.415 美元

每 $50 有效消费的名义期望返奖率 = 1.415 / 50 = 2.83%
```

10,000 抽平均有 200 次获得大于 $5 的奖励，其中平均 10 次获得 $50。此配置将“稀有”具体化为公开概率，不能把它描述成几乎不会出现。

## 5. 整数随机与私有审计

以下 Go 片段是算法示意，不是此次提交的业务实现。表在发布时固定、启动时验证：权重均为正，金额为合法奖项，总权重准确，权重累加不溢出。

```go
import (
    "crypto/rand"
    "errors"
    "math/big"
)

type rewardWeight struct {
    cents  int64
    weight int64
}

// rows 已按规则版本完成验证，total 为所有 weight 的精确总和。
// auditU 仅用于服务端私有审计，不进入用户响应 DTO。
func selectReward(rows []rewardWeight, total int64) (
    cents int64, auditU int64, err error,
) {
    if total <= 0 {
        return 0, 0, errors.New("invalid reward table total")
    }
    n, err := rand.Int(rand.Reader, big.NewInt(total))
    if err != nil {
        return 0, 0, err
    }
    u := n.Int64()
    var upper int64
    for _, row := range rows {
        upper += row.weight
        if u < upper {
            return row.cents, u, nil
        }
    }
    return 0, 0, errors.New("invalid reward table coverage")
}
```

v2 日奖依次抽取 100 格状态分支；普通分支使用 9 行、`total=400` 的奖表，惊喜分支使用 100 格区间选择，再用 `min + randInt(max−min+1)` 抽整数美分。消费抽奖仍为第 4 节的 7 行、`total=1000`。上述通用采样函数用于固定金额奖表，分支／区间选择同样使用 `crypto/rand.Int`；禁止时间种子、`math/rand`、随机字节直接 `% total` 或失败后回退到不安全随机源。

每次成功发奖的操作保存规则版本、各步私有随机整数、中奖金额、幂等键及账务引用；日奖另保存 `daily_low_count` 前后值。利用现有设计中的 `welfare_operations` 保存结果，配合不可变账本，无需另设抽奖结果表。私有审计字段不得随用户结果接口、公开中奖记录或普通页面下发。

用户可以查看消费抽奖公开概率、规则版本和日奖保护的一般说明，不能看到日奖金额表或私有抽样值。服务端用对应版本、抽样前状态和各步随机值重算奖项；这提供内部可核验性，不宣称是用户可独立证明未被操纵的密码学公平协议。

日奖按已确认 v2 的固定状态保护规则执行，所有用户适用同一配置；消费抽奖不增加保底。禁止按用户身份、消费额或运营预算暗中改变概率、库存耗尽替换奖项。若未来修改规则，必须显式发布新版本和生效时间，旧记录仍引用旧版本；不能根据本次随机结果或用户画像选择版本。

## 6. 实际扣费同步生成抽奖资格

合格消费来源为福利上线后 API 账务实际扣除的账户余额，使用这笔结算最终落库的规范金额。不能从请求标价、预估费用、token 数、充值记录、福利兑换记录或随后汇总的 usage 日志反推有效消费；没有实际扣账户余额的订阅额度消耗不计入。

上线边界使用固定持久化的生效时间/资格边界；禁止历史回填或部署时扫描旧账补发。生效边界判断由结算路径统一执行，并由不可变消费事件保存其账务来源。规则版本更新、服务重启和签到周期重置均不重置消费累计。

资格采用**同步结算**：在执行账户余额实际扣费的同一个数据库事务中，记录具有唯一账务来源的不可变福利消费事件，并更新该用户福利钱包中的累计消费和抽奖资格；所有步骤一并提交或回滚。不把即时次数发放委托给延迟 worker，也不依赖之后落库的用量日志。

不涉及退款时：

```text
S_new = S_old + 该笔实际余额扣费
E_old = floor(S_old / 50)
E_new = floor(S_new / 50)
本笔新增资格 = E_new - E_old
消费余数 = S_new - 50 × E_new
```

金额运算始终保留 8 位小数。例如累计 `49.99999999` 后扣费 `0.00000001`，应立即得到一次资格；每笔先舍入到美分会漏计这类消费，禁止这样处理。一笔消费可以跨过多个 $50 档位，必须发放对应的全部次数。

消费事件按结算唯一引用去重；重复结算重试不能再次累计。并发结算必须对同一福利钱包串行化或通过等价原子更新保护累计值，不能用应用层“先读金额、计算、再覆盖”的方式更新。

福利兑换后的余额被用户实际用于 API 时，仍属于合格消费。1:1 兑换本身不产生消费或次数，真正发生 API 余额扣费时才累计。

## 7. 退款建议：净消费资格与次数欠额

本节是建议政策，尚非用户明确确认。退款必须引用原合格账务事件，累计退款不得超过该事件的合格扣费；普通管理员余额调整不能冒充 API 消费退款。

每次退款追加不可变负向消费事件，在同一退款事务内重新计算净消费和资格。不要修改或删除原消费事件。

```text
S = 上线后合格实际扣费总额 - 对应合格退款总额，S >= 0
E = floor(S / 50)                 // 按当前净消费应有的累计资格
U = 历史已经成功消耗的抽奖次数     // 不因退款而抹去
available = max(E - U, 0)
ticket_debt = max(U - E, 0)
```

退款优先撤销尚未使用的资格；若已消耗次数超过退款后的应有资格，记录次数欠额，以后消费新增资格先抵消欠额。建议不自动撤销已经发出的奖金，也不自动扣回主账户余额；其经济影响和用户说明需要随退款政策一起确认。

例：用户累计消费 $100、已抽 2 次；退款 $0.01 后净消费 $99.99，`E=1`、`U=2`，欠 1 次。再消费 $0.01 仅消除欠额，不发可用次数；之后再消费 $50 才产生 1 次可用抽奖。存在欠额时，页面不能仅按普通余数显示“再消费 $0.01 即可抽奖”。

任何时候 `available` 与 `ticket_debt` 都不能同时大于零；抽奖只允许在 `available > 0` 时使 `U` 增加 1。退款和抽奖需要争用同一个钱包并在事务内判定，防止并发使用已被撤销的资格。

## 8. 幂等、随机失败与兑换

以下操作均要求原子提交及稳定重放：

| 操作 | 业务去重依据 | 同笔提交的结果 |
|---|---|---|
| 签到 | 用户 + 服务端业务日期 | 日奖、额外里程碑、daily_low_count、周期进度、累计签到、福利入账及结果 |
| 结算消费 | 原账务结算唯一引用 | 实际扣费、不可变消费事件、消费累计与抽奖资格 |
| 抽奖 | 用户 + 操作类型 + 幂等键 | 消耗 1 次资格、随机结果、福利入账及结果 |
| 兑换 | 用户 + 操作类型 + 幂等键 | 福利扣减、主余额增加、双方账务引用及结果 |

同一幂等键只能对应一个规范化请求。重复请求返回已提交的原操作结果，不重新抽样、不重新扣次数、不重复兑换；同一键搭配不同金额等参数应明确拒绝。原结果中的当时余额是历史快照，最新钱包余额可另行读取，不能为重放而改写历史结果。

随机源失败：签到/抽奖整体失败，无奖励入账、无次数消耗、无签到日期占用、无 daily_low_count 推进。不能发默认小奖冒充抽样成功，也不能把失败记录当成已完成发奖。没有任何已提交结果的失败重试可以重新尝试生成随机数。

若随机值已生成而数据库事务内部自动重试，应在本次请求内复用已生成值；只要结果成功提交，以后所有幂等重试均返回相同结果。连接中断造成提交状态不明时，应先按幂等键查明状态，不能立即再次抽样。未提交、用户从未获得成功结果的回滚事务不构成一条已经完成的抽奖。

兑换金额必须是大于零的整美分，并且不超过可用福利余额。`0.01` 合法，`0.001` 非法；不设置 $1、$5 等额外门槛。兑换比例恒为 1:1，无手续费；一次 $0.01 兑换对应福利 `-0.01000000`、主余额 `+0.01000000`。在同一事务内完成条件扣减和主余额增加，幂等重试不得重复入账。

## 9. 成本预算

以下金额是发放余额的面值，不等于上游模型服务商的真实成本或现金支出。活跃用户不自动等于连续满勤用户，应分别统计实际签到人次与里程碑人数。

```text
D   = 成功签到总人次
H   = 根据各用户起始状态及签到次数，用四状态 DP 计算的期望惊喜日奖人次
N7  = 成功触发第 7 天额外奖励的次数
N15 = 成功触发第 15 天额外奖励的次数
N30 = 成功触发第 30 天额外奖励的次数
K   = 实际成功消耗的抽奖次数

签到名义期望 = 0.0541 × D + 0.15965 × H + 0.60 × N7 + 2.00 × N15 + 5.00 × N30
抽奖名义期望 = 1.415 × K
合计名义期望 = 上述两项之和
```

成熟总体可用 `H≈25D/66` 做稳态近似；新用户必须按初态 0 递推，不能直接套稳态单日期望。以下假定所有人都从状态 0 完成首个连续 30 天周期：

| 成本口径 | 1,000 用户 | 10,000 用户 |
|---|---:|---:|
| 所有人首次签到一次，日奖期望 | $86.03 | $860.30 |
| 首 30 天日奖期望 | $3,401.25 | $34,012.51 |
| 一个完整周期额外奖励 | $7,600.00 | $76,000.00 |
| 首个完整周期签到总期望 | **$11,001.25** | **$110,012.51** |
| 首个完整周期签到理论最低值 | $8,530.00 | $85,300.00 |
| 一个完整周期签到理论最高值 | $37,600.00 | $376,000.00 |
| 长期稳态每完整 30 天签到期望 | $11,037.20 | $110,372.05 |
| 每人另抽一次的抽奖期望 | $1,415.00 | $14,150.00 |
| 首轮满勤且每人另抽一次的合计期望 | $12,416.25 | $124,162.51 |

最后两行必须以确实获得并消耗了一次抽奖资格为前提；签到本身不会自动送一次抽奖。签到成本不能与按同一批实际消费重复估算的抽奖成本二次相加。

### 9.1 奖励余额再次消费的循环影响

单层消费返奖率 `r = 1.415 / 50 = 0.0283`。在所有奖励都会继续用于 API、长期阈值余数能够充分累计且不考虑退款的预算近似中：

```text
额外抽奖奖励相对外部消费的比例
  = r + r² + r³ + …
  = r / (1 - r)
  ≈ 2.9124215293%

外部给定福利本金 A 连同递归抽奖奖励的总面值
  ≈ A / (1 - r)

首轮满勤签到福利期望 A = 11.0012505355 时，总面值近似为 11.3216533246 美元。
```

这是长期或群体预算近似，不能作为单用户必得收益或精确的单周期抽奖期望：个体有 $50 门槛、未消费余额、未使用次数和期末余数。`r < 1` 说明几何期望收敛，不表示每个观察窗口的实际成本都有同样比例上限。

## 10. 算法验收要点

- 枚举四状态各 100 个分支值、普通 400 权重、惊喜区间 100 权重及区间整数分值；验证分支期望 $0.0541／$0.21375。消费抽奖仍单独枚举 1000 权重，不依赖蒙特卡洛小样本证明概率。
- 验证最多 3 次连续普通，daily_low_count 跨漏签／月份／第30→1天持久保留；里程碑奖励不影响日奖分类。初态 0 首 30 次期望用 DP 核对，不能按独立日计算。
- 第 7/15/30 天额外奖励与日奖同时到账；第 30 天后重新第 1 天，累计签到不清零；漏签重置本轮。
- 未领取及部分已领取状态下，用户 rules／overview、活动规则、页面和隐藏属性不泄露未来里程碑金额；前端不内置该金额表。成功结果与本人流水正确显示已到账金额，日奖／抽奖公开规则与后端连续奖励计算不变。
- `49.99999999 + 0.00000001` 正确越过 $50；一笔跨多个档位全部发资格；原结算幂等重放不多发。
- 实际扣费、消费事件和资格更新同事务；任何一步失败全部回滚。
- 同日重复签到、重复幂等键、并发抽奖、并发兑换都不重复记账、不超支。
- 随机源异常不扣次数；成功结果重放不重新随机；公开接口不含私有审计 `u`。
- $0.01 可兑换；不足一美分及超额金额被拒绝；金额 API 不输出浮点数。
- 若采用建议退款政策，验证未用资格撤销、已用资格欠额、未来资格先抵欠额以及退款与抽奖并发。
