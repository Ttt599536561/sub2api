## 1. 公共数据与断言

- 固定系统时区为 `Asia/Shanghai`，固定服务端决策时间 `T=2026-09-06 12:00:00+08:00`。边界用例通过可控时钟推进，不用真实等待。
- 用户 U1 有两份不同月卡分组订阅：A 每日 100，B 每日 200。默认均有效、用户和分组启用、允许提前重置、还有 10 天有效期、今日次数 0、版本 10。
- 除特别注明，周/月限额不设置，自动开关关闭；日窗口起点为当天 0 点。
- U2 有独立订阅 C；非月卡分组 W 不允许提前重置。
- 成功断言 S：仅目标订阅每日已用变为 0；到期时间准确减少 86400 秒且仍晚于决策时间；今日次数增加 1；版本增加；存在且仅存在一条匹配事件；周/月用量、日上限、余额、其他 Key/账号额度和历史账单不被清零。
- 拒绝断言 F：没有提前扣天、没有成功次数增加、没有成功事件；允许原本到期窗口的自然维护独立完成，但不得把其记为付费重置。
- 重放断言 I：返回原操作结果或明确的结果查询状态，不能再次扣天或重复计数；订阅在此期间的新消费不能被第二次清空。

## 4. 并发、幂等及结算顺序

使用真实 PostgreSQL 事务和两个独立连接，通过屏障控制读、锁、提交时序。不能只用内存 mock 声称验证了数据库并发安全。

| ID | 需求 | 前置与步骤 | 预期 |
| --- | --- | --- | --- |
| C01 | R06 | 同一个操作 ID 并发提交 20 次 | S 一次，其余 I；只扣一天 |
| C02 | R06 | 两个不同操作 ID 携带同一轮次版本并发手动重置 | 最多一次 S；另一条返回状态变化，不再扣天 |
| C03 | R06 | 自动任务与手动点击对同一耗尽轮次同时执行 | 最多一次 S；额度、计数、流水一致 |
| C04 | R06 | 两个后端实例同时自动检查同一订阅 | 最多一次 S；不依赖进程内锁保证正确 |
| C05 | R06 | 第一条已成功，随后新消费产生 1 刀，再重试旧操作 ID | I；新产生的 1 刀不能被旧操作抹掉 |
| C06 | R06 | 第一条已成功并产生新消费；用户刷新后发起新操作 ID 和新版本 | 正常 S，符合“只要消费过就能手动重置” |
| C07 | R06 | 同一操作 ID 改目标参数/版本后重试 | 冲突，无第二次扣减 |
| C08 | R07/R09 | 只剩一次可扣时长或一次今日名额，100 个并发操作 | 最多一次 S，不超过有效期和次数边界 |
| C09 | R15 | 费用事务先提交，再执行重置 | 已提交日用量被清零；周/月及日志保留 |
| C10 | R15 | 请求先开始，重置先提交，请求费用后提交 0.8 | 重置后日用量为 0.8；不能丢掉或重复累加 |
| C11 | R15 | 多个请求跨重置边界完成，总费用由串行化屏障确定 | 每笔费用只结算一次；日用量等于重置后提交费用之和 |
| C12 | R15 | 同一计费请求重复回调/重试，自动开关开启 | 沿用原计费去重，不重复累计、不因重复通知重复扣天 |
| C13 | R13 | 自然日刷新和提前重置竞争同一订阅 | 结果符合锁内决策日期；旧自然刷新不能再次清掉新一轮消费 |
| C14 | R07 | 续费增加 30 天与重置减少 24 小时同时发生 | 两个合法变更都保留，不能因旧快照覆盖另一方 |
| C15 | R07 | 管理员缩短有效期与用户重置竞争 | 基于锁后时间重新校验；不负扣、不覆盖管理员更新 |
| C16 | R06 | 管理员日额度清零与用户重置竞争 | 旧用户轮次失效，不在管理员清零后无消费时扣天 |
| C17 | R06 | 关闭自动开关与已经排队的自动任务竞争 | 关闭先提交则任务 F；任务先提交则最多保留该次合法事件，随后停止 |
| C18 | R01 | 管理员关闭组许可与重置竞争 | 按事务顺序判断，关闭后新操作不得继续成功 |
| C19 | R06 | 同时重置 A、B | 互不串卡；锁粒度不会把所有月卡串行化 |
| C20 | R06 | 同一秒内完成重置、产生新消费、再合法重置 | 独立递增版本区分两次操作，不依赖秒级 UpdatedAt |
| C21 | R06 | 开启请求响应丢失，用户随后关闭，再重放旧开启请求 | 旧版本不能把自动开关重新打开，回读用户最新选择 |

| A10 | R05 | 保存开关成功，但即时重置临时失败 | 明确显示偏好已保存、额度尚未重置；后续补偿不重复扣天 |
| A11 | R06 | 重置订阅更新后、写事件前注入数据库错误 | 整笔提前重置回滚，额度/天数/次数均不改变 |
| A12 | R06 | 写事件后、提交前终止连接 | 事务回滚或待查；以操作查询核实，不盲重试新 ID |
| A13 | R06 | 数据库已提交，HTTP 响应丢失 | 查询/同 ID 重试得到同一成功事件，仍只扣一天 |
| A14 | R06 | DB 提交成功后 Redis 清理失败 | 已成功的扣减不重做；权威数据库准入仍正确，记录缓存故障 |
| A15 | R06 | 注入重置前发起、重置后才完成的旧缓存回填 | 不能恢复旧有效期或旧日用量用于准入/再次扣天 |
| A16 | R06/R15 | 清缓存并加载新快照后，投递旧的延迟用量增量 | 不造成权威每日用量重复累计或误触发重置 |
| A17 | R06 | Redis pub/sub 消息丢失，一个实例保留旧 L1 | 该实例不能靠旧缓存放行已无资格请求或重复扣天 |
| A18 | R07 | 数据库不可用，Redis 留有旧订阅 | 拒绝需要权威数据的操作，不依据旧缓存扣天或猜测成功 |
| A19 | R05 | 长期没有新请求但自动开关开启、DB 中日用量已满 | 周期补偿仍会检查，不要求用户刷新页面 |
| A20 | R12 | 自动重置尝试失败，而原消费已经提交 | 原消费保持，不因重置失败而回滚或丢失 |

## 9. 性能与发布验收

- 对比功能关闭、月卡功能开启但未触发、持续触发重置三种负载，记录请求吞吐、p50/p95 延迟、DB 连接池等待、SQL 次数和自动检查延迟。
- 使用至少两个服务实例验证同订阅竞争，不能只验证单进程锁。
- 模拟页面之外的 API 客户端，覆盖 Anthropic/OpenAI/Gemini 的公共订阅计费入口，确认不能因供应商分支漏接而只对部分月卡生效。
- 全部安全用例必须通过，并与 R01-R19 的已确认产品规则保持一致。若 DB 权威读方案的性能不可接受，应先评审设计调整，不能绕过正确性要求。
- 提供前端桌面/移动端截图、失败注入结果及迁移前后关键数据对比。没有运行的检查必须明确列为未执行。
