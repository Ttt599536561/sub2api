# 邀请福利月卡补充码与分组保护

日期：2026-11-16（Asia/Shanghai）。基于主仓 main / f7ce04c68；仅本地开发与验证，未推送、发布镜像或部署服务器。

## 管理员操作

兑换码管理 → 生成兑换码 → 类型“订阅” → 用途“邀请福利月卡”，选择邀请活动。服务端从活动读取固定订阅分组，界面显示名称及ID。选择“福利月卡加额”填写每张增加的月总额度，或选择“福利月卡加时”填写增加天数；数量和兑换码本身的过期时间仍可配置。

补码只适用于兑换用户在相应分组下已有的active、未过期、未关闭福利周期。无卡、已过期、暂停或撤销状态均拒绝，码保持未使用。不自动创建新月卡、不修改同组普通订阅。额度耗尽或为0但周期仍有效时允许补充；剩余额度为max(0,总额度-已用量)，不保证原有超额用量下立即增加等额剩余。

- 加额增加本周期月总额度，保留原到期时间、已用量、日/周限制和窗口。
- 加时从原到期时间加天数，保留额度、用量和原周期ID；跨过30天也不刷新月额度。
- 活动版本、名称、分组和增量在生成时记录；改活动名称/文案/停用只改变配置版本，不作废补码。兑换仍验证当前绑定相同、分组有效且属于订阅类型。
- 每张补码的独立流水记录实际周期与变更前后值；管理列表、兑换结果和历史显示面额及兑换时快照，历史快照不是当前余额。
- 普通订阅码、充值余额码和缺省新字段的历史码维持原规则；已分配QQ奖励仍按原邀请来源授予额度。补码不允许进入QQ活动库存。

## 分组保护和并发

260迁移在数据库侧保护当前/历史活动绑定、福利权益、补码与历史账本引用：禁止软删/硬删对应分组，禁止改成非订阅类型，允许改名、描述和未来额度配置。既有福利快照不会被分组额度修改重算；同名新分组也不会继承旧码。

删除保护先于级联修改，返回409与关联活动、未用补码、福利订阅和历史数量。草稿活动产生补码后也不能更换绑定分组。停用分组会阻止补码生成和兑换；本次不新增历史权益迁组功能。

组破坏性操作自有事务使用Read Committed，读取引用前持组锁；引用写入以SHARE组锁协调。调用者事务保留所有权；外部Repeatable Read事务的破坏性操作拒绝重试，防旧快照漏掉刚提交的引用。名称等普通修改不受此限制。

补码按code→user→campaign→group→subscription锁序原子核销、更新权益并记账。QQ库存导入先按ID锁定候选码，再锁活动/分组，修复“导入一个最终会拒绝的补码”与有效兑换产生的反向锁等待。月额度使用数据库NUMERIC运算；手动收据与QQ授予表隔离，退群只追回原QQ额度，保留手动增量与时长。两种补充均推进管理员调整版本，不改变QQ授予次数。

每个周期另存当前仍有效的手动加额归属（独立projection表，不混入不可变收据）。补码增加该值；管理员设置总额时将该值裁至不超过新总额；退群扣原QQ奖励时保留这部分且绝不提高当前总额。独立审查发现并复现“QQ100→管理员设0→补20→退群误扣成0”，据此补齐该边界；不是简单按历史补码SUM设置下限，以免恢复后来被管理员明确削减的额度。
