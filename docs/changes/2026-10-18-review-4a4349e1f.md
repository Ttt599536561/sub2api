## 确认的问题与修复

### UF-R8 / P2：SSE 头里的失败终态没有补齐计费快照

普通 Responses 与透传都支持仅由 `event: response.failed` 指明事件类型、JSON 不带 `type` 的上游。然而新增标记函数只解析 JSON，后续失败帧被误当成非终态；先发裸 cyber error 的情况下，首次 0 token 永久保留。

真实 `Forward` 回归在两个入口均复现：后续终态包含 1200 输入、300 输出和 200 缓存读取 token，标记输入仍为 0。修复增加携带已解析事件类型的内部入口，保留 JSON type 优先和原 JSON/WS 调用方式。两个入口现在补齐终态事实并按 Ultrafast 8× 完整结算；首次审计信息不变。

### UF-R9 / P2：透传模型恢复污染响应模型计费

compact 回退可能把真实上游模型改为较便宜的模型；透传对客户端恢复原始请求模型后，错误快照再次解析这个改写后的 payload。渠道启用 `response_model` 定价时，正常结果依据真实上游模型降价，cyber 错误却把较贵的客户端模型当成上游声明。

真实 `Forward` 两次发送夹具复现相同 token 下正常费用 `$0.00001815`、cyber 费用 `$0.00044`。修复在客户端模型/工具名称恢复前复制错误帧，风控审计和计费使用原始上游声明；客户端响应沿用原恢复逻辑。永久回归比较 default、response_model、requested、channel_mapped 四种来源的成功/错误结算。

核实排除：透传显式 `BillingModel=reqModel` 与正常默认计费一致，因为 `forwardResultBillingModel` 优先请求模型；本轮不改变这条定价规则。

### UF-R10 / P2：Chat/Messages 在裸错误处过早停止读取

上游先发裸 cyber error，后发包含真实用量的 `response.failed` 时，兼容流收到第一条错误即返回，新增终态补齐逻辑无法执行。真实 Chat 与 Messages 流式转发都复现 1200 输入 token 被记为 0。继续核对发现，stream=false 的共享缓冲读取器把裸错误合成为终态时还会丢掉嵌套的 error.code，导致 cyber 风控标记完全缺失。两类问题沿本次新计费快照调用链确认；停止读取的旧行为早于被审查提交，本次补齐遗漏。

修复为兼容流和缓冲读取器保留首个原始 cyber 证据，并用最长 2 秒的总时限读取后续终态。重复错误或心跳不延长时限；EOF、DONE、读取异常或超时保留原拒绝，不换号重放。客户端错误只发送一次，后续终态仅补齐计费事实。永久测试覆盖同步/keepalive 两种读取模式、流式/缓冲、重复错误、延迟终态、EOF、DONE 和持续心跳下的等待上限。后续非 cyber 的失败或完成终态可以补齐已有标记的计费事实；没有先前 cyber 证据的请求不会凭空创建标记。独立复核确认没有重复输出、换号或双扣路径。
